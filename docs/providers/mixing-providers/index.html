Mixing providers

One instance across Vercel, Supabase and AWS S3. Placement slots, how credentials pass between providers, the variables the frontend gets, and triggers.

Each placement slot of a template can go to a different provider, so you can put every part of an app where it costs least. This page follows the built in Web app on managed platforms template (web-platforms) with a common low cost layout:

  • the website on Vercel,
  • PostgreSQL on Supabase,
  • uploads in an AWS S3 bucket.

Preview

The Vercel and Supabase adapters are in Preview: covered by unit tests, not yet verified against live accounts.

The template

accessKeys: true on files matters here: a Vercel app cannot assume an AWS role, so the AWS module creates an access key limited to this one bucket for it.

Bind the slots

Register three targets

Register one cloud target per provider: a Vercel team, a Supabase organization and an AWS account. Each has its own credentialRef.

The Vercel region sets where its functions run, so put it next to the database.

Review the plan and deploy

The plan shows the capability chosen for each resource (vercel-project, supabase-postgres, s3), the cost estimate and the connectivity strategy. web and database are on different providers, and the template asks for mode: secure, so the plan picks public-tls: TLS over the public network. Supabase connection strings carry sslmode=require. See plan and cost.

The deployment follows the dependency graph: database and files first, then web, which depends on both.

How credentials pass between providers

The frontend needs the database password and the bucket key, but those belong to other providers. OrkStage moves them at deploy time without keeping a copy:

  1. database and files publish only a reference in their outputs (secret_ref), never a value.
  2. When the Vercel adapter deploys web, it asks OrkStage for the credentials of each dependency that has a secret_ref.
  3. OrkStage calls readSecret on the adapter that owns the dependency, with that target's own credentials:
    • Supabase derives the database password again from the OrkStage encryption key. It is never stored anywhere: it was derived the same way when the project was created.
    • AWS reads the bucket key from the Secrets Manager secret the module created in your account, using the deployment role.
  4. The Vercel adapter writes the values to the project as sensitive environment variables, which Vercel never shows again.

The values pass through the control plane's memory only. They are not written to the OrkStage database, outputs or logs. The S3 key itself lives in your AWS account: in the OpenTofu state in your state bucket and in the Secrets Manager secret. Its IAM policy allows s3:ListBucket, s3:GetBucketLocation, s3:GetObject, s3:PutObject, s3:DeleteObject and s3:AbortMultipartUpload on that bucket only.

What the frontend receives

Variable names come from the resource id: database becomes DATABASE, files becomes FILES (upper case, any other character turned into _). Connection settings from outputs are added as <ID>_HOST, <ID>_PORT, <ID>_URL, <ID>_BUCKET, <ID>_ENDPOINT and <ID>_REGION. Each credential field becomes <ID>_<FIELD>, with camel case turned into upper snake case (poolerUrl becomes POOLER_URL, secretAccessKey becomes SECRET_ACCESS_KEY). When a name comes from both, the credential wins and the variable is stored as sensitive.

Vercel functions connect over IPv4, and the Supabase direct host is IPv6 only unless the project has the paid IPv4 address option. Use DATABASE_POOLER_URL from the app.

Other placements

The same template accepts other providers in each slot. What changes:

SlotChoiceWhat to know
webRender static siteEnvironment variables are available at build time only.
dataRender PostgresThe frontend also gets DATABASE_INTERNAL_URL. Render Postgres offers only restart, so nightly-backup is unavailable.
dataGoogle Cloud or AzureNot reachable from Vercel as is: a Cloud SQL instance without a network accepts only Cloud SQL connectors, and an Azure server with publicAccess accepts Azure services only.
filesSupabase StorageThe bucket must depend on the Supabase database (add dependsOn: [database] to files). The frontend gets FILES_URL, FILES_SERVICE_ROLE_KEY and FILES_ANON_KEY instead of an S3 key.
filesGoogle Cloud, Azure or DigitalOceanThe frontend gets the bucket name, endpoint and region, but no credentials: only the AWS adapter creates keys for accessKeys today.
