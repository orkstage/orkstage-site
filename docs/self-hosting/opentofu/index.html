OpenTofu runner and state

How OrkStage runs OpenTofu in throwaway runners on Docker, ECS or Kubernetes, keeps one state per resource, plans before apply and scans for drift.

OrkStage provisions AWS with OpenTofu modules in infra/tofu/modules/aws/*, one module per logical resource type. ADR 0005 records the design.

The isolated runner

  • The worker never runs OpenTofu in its own process. OpenTofu runs in a throwaway runner: the pinned ghcr.io/opentofu/opentofu:1.13.2 image, or the tofu-runner image with the modules baked in.
  • The module library is mounted read only, or baked into the image. Providers come from a plugin cache that all runners share.
  • Credentials reach that one runner only. They never appear in command lines, task or Job definitions, or state.
  • Each run has a hard timeout (TOFU_TIMEOUT_MINUTES, 45 by default) and can be cancelled.

Where the runner runs

TOFU_RUNNER chooses how the worker starts runners (ADR 0016).

TOFU_RUNNERRunnerWhat the worker needs
docker (default)A container per command on the worker's Docker hostThe Docker socket, which gives it control of that host. Run it on a host used only by OrkStage.
ecsOne ECS task per operationecs:RunTask, ecs:DescribeTasks, ecs:StopTask and iam:PassRole on the runner's execution role. No socket.
kubernetesOne Job per operationcreate, get and delete on Jobs and list on pods in its namespace. No socket.

With ecs and kubernetes, one operation (an apply, a plan, a drift scan, a destroy) runs init, validate and its commands in a single task or Job, so it waits for one start, not four. The worker and the runner share the work directory through a volume, and the runner image must carry the modules (TOFU_MODULES_IN_IMAGE=true). Credentials travel in a file on that volume that only the runner's user can read and that the runner deletes before OpenTofu starts: they are never in the RunTask call (which CloudTrail records) or the Job manifest. The runner runs as the worker's user (10001 in the platform image) with a read only root file system.

ECS

  1. Create an EFS file system with an access point for user and group 10001, encrypted in transit. Mount it in the worker task at TOFU_WORK_DIR (for example /var/lib/orkstage/tofu).

Each Job runs as the worker's user without a service account token, privilege escalation or capabilities, with backoffLimit: 0 and a deadline of TOFU_TIMEOUT_MINUTES; the worker deletes it when the run ends or is cancelled. A runner image that cannot be pulled fails the run at once.

One state per resource

The state key is orkstage/<physical-name>.tfstate. There is one state for each resource, not one for each instance or placement slot. This design:

  • keeps the platform's own DAG, with progress, retries and failure isolation for each resource;
  • limits the damage of a broken state file to one resource;
  • passes dependencies as module outputs that become inputs of the next module. Every module emits a kind output, so the adapter wires them by type;
  • stores the exact root configuration next to the state (.config.json), so a destroy never depends on a template that has changed since.

Backend: S3, with use_lockfile for locking, and encryption. On real AWS, you create the bucket in advance with versioning and encryption, and OrkStage validates it before use (see Connecting an AWS account). On an emulator, OrkStage creates the bucket on first use.

No secrets in state

An OpenTofu ephemeral resource generates each RDS master password, and the module writes it through write only attributes (password_wo, secret_string_wo). Services receive the ARN of the Secrets Manager secret as an ECS secret. We verified that the state holds password: null.

Provider plan before apply

In the Generate plan phase, the worker runs a real tofu plan for every existing resource whose desired state changed. It writes a summary for each resource to the deployment's event log:

  • A deletion or replacement makes the deployment high risk. A routine new revision of an ECS task definition (for a new image digest) does not.
  • For a production instance, high risk escalates the deployment to AWAITING_APPROVAL, even when the platform's own diff predicted only an update.
  • A resource the provider could not plan also escalates a production deployment to approval: nobody approves changes nobody has seen.
  • When no change is destructive, the approval step is marked skipped, with the reason.
  • The deployment stores the provider plans (plan.providerPlans) for review.

What is approved is what is applied

Every OpenTofu command runs tofu validate after init, so a configuration error stops before any plan or change.

The plan phase saves each provider plan to a file named after the deployment, in that resource's working directory, next to a hash of the configuration it was made from. The apply phase then runs tofu apply <plan file> instead of planning again:

  • If the configuration changed in between (for example a dependency was replaced earlier in the same deployment), or the state changed (someone deployed or edited the resource), a production step fails with a message that says so, and nothing is applied. Deploy again to plan and approve the current changes. Other environments log a warning, plan again and apply.
  • The plan file holds attribute values, so it is used once and deleted, whether the apply worked or not. Retries of a failed step plan again.
  • Resources this deployment creates have no saved plan: the platform plan already lists them as new.

Previews and drift scans plan in working directories of their own, without the state lock, so they never touch the directory of a running deployment.

Drift scans

Every DRIFT_CHECK_INTERVAL_MINUTES (360 by default, 0 turns scans off), the worker plans each applied resource on real providers again, from the snapshot it was deployed with. Any planned action means someone changed the resource outside OrkStage. The resource then becomes DRIFT_DETECTED, OrkStage writes an audit event and sends instance.drift_detected. The scan skips resources with pending changes. A new deployment restores the configuration from the template.

Recovery from deleted resources

When someone deletes a resource outside OrkStage, its recorded state outlives it. The AWS adapter has a live existence probe for this case:

  • During verification, OrkStage probes any resource that is not healthy. If the resource no longer exists, the step fails at once with Resource no longer exists at the provider. Redeploy to re-create it. instead of waiting.
  • Verification waits in one settle window of 5 minutes per deployment, not one per resource, so a slow service does not multiply the wait.
  • On the next deployment, the executor asks the provider whether converged resources still exist. It recreates the missing ones instead of skipping them as unchanged.

Verified against MiniStack

The AWS adapter has been tested end to end against MiniStack with: VPC, subnets and security groups, ECR, SQS with a dead letter queue, S3, Secrets Manager, RDS Postgres (real container), an ElastiCache Valkey replication group (real container), an ALB with target groups and listener rules (live data plane at /_alb/<name>/), an ECS Fargate service (real container, registered in the target group and healthy), Route 53 and ACM. The adapter contract suite passes against it.
