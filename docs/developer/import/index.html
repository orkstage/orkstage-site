Importing infrastructure code

How the IaC import API and scan engine work. Supported sources, mapping rules, the ScanReport v1 format and the calls that create a draft template.

An import turns infrastructure code into a draft template that you review. One engine, orkstage-scan (written in Rust), does all detection and mapping. The ork CLI runs it natively, and the platform runs it compiled to WebAssembly (@orkstage/scan).

Supported sources

Source kindWhat the engine reads
terraform.tf and .tf.json files; variables, locals, local modules, resource references
cloudformation, sam, cdkTemplates in YAML or JSON, including tags in short form; synthesized CDK output
kubernetes, helmDeployments, Services, Ingresses, StatefulSets; Chart.yaml
composeServices, ports, images and dependencies in docker-compose.yml or compose.yaml
dockerfileBase images and exposed ports
packagepackage.json, go.mod, requirements.txt and similar files, as hints (for example a Postgres driver)
pulumi, serverless, bicep, armDetected and reported

Detected resources map to the nine OrkStage types: network, compute.container-service, container-registry, database.postgresql, cache.redis, queue, object-storage, ingress and dns. Anything else appears in the unmapped list with a reason. Nothing is dropped silently.

Mapping rules in short

  • When several sources show the same component, it becomes one resource that keeps every source. For example, a Compose postgres service, pg in package.json and an aws_db_instance become one database.postgresql on AWS.
  • Evidence strength, from strongest: IaC, then Kubernetes, then Compose, Dockerfiles and package hints.
  • References become connections, for example a task definition that reads aws_db_instance.main.address.
  • The engine adds a network when services or data stores need one. It adds an ingress and DNS when a public HTTP service runs on a cloud provider.
  • Placement slots are chosen per provider: primary for the compute provider, and slots such as data, storage and messaging for the others. The engine also tags the template with its size (starter, growth or scale) and its contents.
  • Each resource has a confidence of high, medium or low.

API flow

Create the import

To let the server scan the files instead, send them as text:

Send either files (text only, at most 2000 files and 5 MB in total) or report, never both. The response is an ImportDto:

A report that is not a ScanReport version 1 gets 422 INVALID_REPORT.

Review

Call GET /api/v1/imports/:id, or open https://<console>/templates/import?importId=<id>. Check report.resources (with sources and confidence), report.unmapped, report.connections, report.warnings and validation.issues.

Create the draft template

The response is { templateId, name, version: "0.1.0", status: "DRAFT" }. The API sets the name, display name and version in the YAML document itself, so the formatting and comments of the generated template survive. Templates are shared by all tenants, so this step needs a platform role: with an API key, an organization key with the PlatformAdmin role.

Possible errors: 409 ALREADY_CONVERTED (an import produces one template at most), 409 TEMPLATE_EXISTS, and 422 TEMPLATE_INVALID with the issues.

Then edit the draft in the builder, validate it and publish it. Both the import and the template creation are audited.

Using the engine in Node.js

The WebAssembly build is packaged as @orkstage/scan. You build it from the cli/ folder with scripts/build-wasm.sh. It is not published to a registry yet.

scanFiles(files, options?) is synchronous and does no I/O. The options are templateName, displayName, templateVersion and maxFileBytes.
