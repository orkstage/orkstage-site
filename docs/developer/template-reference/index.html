Template reference

The platform/v1 EnvironmentTemplate format. Metadata and tags, placement slots, variables, every resource type with defaults and limits, and examples.

A template describes intent, never provider resource blocks. The schema on this page comes from packages/templates/src/schema.ts, the source of truth for the API, the console builder and the CLI.

Identifiers

Resource ids, slot names and variable names match ^[a-z][a-zA-Z0-9-]{0,39}$. They start with a lowercase letter, continue with letters, digits and dashes, and have at most 40 characters.

Placements

A placement slot is a named group of resources that an instance binds to one cloud target and region.

FieldTypeDefaultNotes
nameidrequiredResources refer to it in their placement field.
descriptionstring
providersenum[][] (any)Allowed providers: aws, azure, gcp, oci, digitalocean, vultr, coreweave, magalu, vercel, render, supabase, mock. An empty list allows any registered provider. See providers.

A network binds implicitly only to resources in its own slot. A database placed on another cloud therefore does not depend on the AWS VPC.

Resources listed in dependsOn reach the frontend as environment variables. Connection settings arrive in plain text (<ID>_HOST, <ID>_PORT, <ID>_URL, <ID>_BUCKET, <ID>_ENDPOINT, <ID>_REGION); credentials a dependency publishes arrive as encrypted values, one per field (<ID>_URL, <ID>_USERNAME, <ID>_PASSWORD, <ID>_ACCESS_KEY_ID, <ID>_SECRET_ACCESS_KEY, and so on), read from the provider that owns the dependency at deploy time. <ID> is the resource id in upper case with dashes turned into underscores.

Connectivity

FieldTypeDefaultNotes
from, toidrequiredResource ids.
protocolenumrequiredtcp, http, https, postgres, redis, amqp.
portinteger1 to 65535.
modeenumprivate-preferredprivate-required, private-preferred, secure.

When the two resources are on different clouds, private-preferred falls back to TLS over a public endpoint with an allowlist. The plan rejects private-required across clouds. See connectivity in the plan review.

Triggers

A trigger is a named action on one deployed resource, with default parameters: redeploy a frontend, restart a service, take a database restore point. Prefer a catalog action (service.restart, see Triggers): it means the same on every provider. A provider's own action name works too. The console and GET /instances/{id}/triggers list each trigger with its parameters, risk and required role.

FieldTypeDefaultNotes
nameidrequiredUnique in the template.
descriptionstring
resourceidrequiredThe resource the action runs on.
actionstringrequiredA catalog action such as service.restart or database.snapshot, or a provider's own name such as promote.
rolestringCustomerDeveloper, CustomerAdmin or CustomerOwner: raises the role needed to run it, never lowers it.
paramsmap{}Default parameters, checked against the action when it runs.
overridablestring[][]Parameters a caller may change at run time. Anything else is rejected.
on.manualbooleantrueRun from the console or the CLI.
on.webhookbooleanfalseRun with an API key holding instances:deploy, for example from CI or a CMS.
on.schedulecronFive field cron expression in UTC, for example 0 3 * * *. Not for the release actions, which only run by hand or from CI.

See triggers for running them and following their runs.

How deployments of the template reach traffic and how long they are watched. Each deploy can change these; see releases and rollback.

FieldTypeDefaultNotes

Example: the multicloud reference

This example places the API on AWS, the database on Azure and object storage on OCI. Bind each slot to a real target of that provider, to a simulation target that imitates it, or bind every slot to the same AWS target for the AWS only variant. The Azure and OCI adapters are in preview (see providers).
