CI/CD intake

Connect pipelines to OrkStage. Register applications, publish image versions by digest, validate templates in pull requests, then deploy and wait.

Three endpoints exist for pipelines. Pipelines also use the regular deploy and deployment endpoints.

MethodPathScopeBody and result
PUT/api/v1/applications/:nameapplications:write{ displayName, repository, port, registryKind?, healthPath?, readinessPath? }
POST/api/v1/applications/:name/versionsapplications:write{ version, imageUri, digest: "sha256:…", architectures? }

POST/api/v1/instances/:id/deployinstances:deploy{}, returns 202 and a deployment summary
GET/api/v1/deployments/:id/events?after=instances:readProgress events

Register the application

Every image version belongs to an application in the catalog. Create the application from the pipeline before the first publish. The call is idempotent: the same body sent again changes nothing, so you can run it on every build.

  • A name has 2 to 63 characters: lowercase letters, digits and dashes, starting with a letter. Other names get 422 INVALID_NAME.
  • registryKind is ecr (the default), acr, ocir, gar, dockerhub, ghcr or other. healthPath defaults to /health.
  • The response contains "created": true the first time. Every change is audited as CREATE or UPDATE on Application.
  • The catalog is shared by all tenants, so the call needs an organization key with the PlatformAdmin role and the applications:write scope.

Publish an image version

Templates refer to images through the application catalog (image: catalog://orders-api). When OrkStage compiles an instance, each reference resolves to the most recently published version of that application, by digest. A deployment therefore always runs an immutable image.

  • digest must be sha256: followed by 64 lowercase hex characters.
  • architectures defaults to ["amd64"].
  • Versions are immutable. Publishing a version again with the same digest is idempotent (the response has "idempotent": true). With a different digest it fails with 409 VERSION_EXISTS.
  • Every publish is audited as PUBLISH on ApplicationVersion.
  • Publishing needs the same organization key as registration: role PlatformAdmin, scope applications:write.

Validate a template in a pull request

The validation endpoint is stateless. It needs no template id and stores nothing.

The report lists every issue with its stage, severity, code, message and path.

Deploy and wait

If you deploy while another operation is running, the API answers 409 INSTANCE_BUSY. Treat it as "try again later", not as a failed build.

GitHub Actions

To keep publishing and deploying apart, use two keys: an organization key with the Image publishing preset for the publish step, and a tenant key with the CI/CD deploy preset for the deploy step.

Notifications instead of polling

Subscribe a webhook to deployment.succeeded, deployment.failed and deployment.awaiting_approval. Your systems then react to the result without a job that keeps polling.
